Overview and design

1. Background and prototype status

HeatWave Audit Center is an independent prototype for exploring row-change auditing with OCI MySQL HeatWave. It brings connection setup, table registration, capture controls and audit-history exploration into one web application on an Oracle Linux 9 Compute VM.

This is a prototype for evaluation, demonstration and rehearsal. It is not an Oracle product and is not supported or endorsed by Oracle. Oracle service names and architecture symbols describe the integration; they do not imply Oracle authorship, certification or a production guarantee.

The aim is to retain evidence of changes to registered tables: what a row contained before and after an INSERT, UPDATE or DELETE; which source position and queue delivery produced it; and how activity changes over time. The target stores audit history rather than maintaining a current-row replica.

Audience and scope

Operators use the Dashboard, Control Center, Message Explorer and Audit Center. Application administrators also manage configuration, resources, capture positions and retention. An OCI administrator prepares IAM and networking; a database administrator prepares schemas, users and supported source settings.

This manual describes the repository implementation as reviewed on 28 October 2026, including the lifecycle, diagnostic and coverage clarifications. Screenshots show representative sample records, not a live OCI acceptance test. Endpoint names, resource identifiers and CIDRs are examples. Never copy the example identifiers into a real deployment.

What is available

  • Native OCI Streaming capture for one table, database wildcards or all-database wildcards; grouped audit targets; complete images when recorded; GTID initialization, replay checks, typed-key lookup and charts.
  • Conditional large-event fragmentation, durable reassembly, PUT batching/byte pacing and adaptive GET polling.
  • Public schema evidence with available before/after definitions and semantic differences; SQL inspection is used for DDL evidence.
  • OCI Container Instances lifecycle and image replacement, same-compartment resource management and explicit partition cleanup.

Important boundaries

User/privilege auditing needs a separately configured database-audit collector; it is not implemented here. DML binlogs do not establish a complete actor or privilege history. Automatic fleet scaling, verified archive export/restore, fingerprint-key rotation and a dedicated schema-comparison browser are not implemented. Validate the chosen deployment, recovery and capacity before relying on it.

Row-audit coverage: partition exchange, partition drop/truncate and other DDL can change many rows without individual row-image events, even with ROW/FULL. Schema evidence, fingerprints and event charts cannot establish complete data-change coverage. See Appendix I and audit limitations.

Overview and design

3. Deployment architecture

The OL9 application VM manages registered resources with its instance principal. A private Container Instance runs embedded Debezium Engine and the OCI Java SDK; another runs the Python history writer and OCI Python SDK. Both use resource principals for workload access. Private registry images are digest pinned.

Source and target database endpoints attach to the database subnet. Regional Streaming, Vault, Registry and HeatWave services sit outside the VCN boundary; private attachments are shown separately. CIDRs are illustrative examples.

The target contains audit payloads, deduplication evidence, routes, fragment custody, delivery checkpoints, complete source offsets and private JDBC schema history. Source and writer restarts preserve those namespaces. A full target outage can therefore pause capture as well as apply; source binlog retention remains essential.

5. Data flow, fingerprints and evidence

A row change passes through source binlog, embedded Debezium Engine, the data stream and the history writer. Schema events use a separate single-partition stream. Source recovery uses target-backed full offsets and JDBC schema history. Small events remain single messages. Large events are framed and reassembled before normal audit writes; partial fragments are never audit rows.

The writer validates events, computes identities, writes fresh payload/deduplication evidence, and saves target delivery checkpoints before acknowledging in memory. These are recoverable stages, not a single distributed transaction. Durable fragment custody can permit delivery progress before the whole event arrives.

  • Row-key fingerprint: keyed hash of canonical typed source identity, actual database/table and complete primary key.
  • Before/after fingerprints: keyed hashes of observed row content.
  • Event/delivery identity: immutable source coordinates identify supported DML replays; stream coordinates describe deliveries. A GTID alone does not identify each row event.

Canonical JSON preserves types and sorts object keys. {"id":1042} differs from {"id":"1042"}. Preserve the fingerprint secret and source identity with retained history. Automatic stitching of histories across a primary-key change is not implemented.

Setup and installation

6. Installation prerequisites

Deployment is supported on Oracle Linux 9 only. Use the non-root application owner with sudo and an architecture-compatible Python 3.12+ environment. The installer uses app-managed MySQL 9.x, Gunicorn/systemd, rootless Podman, Java and Maven dependencies.

Prepare before installation

  1. Choose an OL9 Compute VM and the one compartment that will contain this deployment's resources and network attachments. Confirm region, capacity and service availability.
  2. Have the OCI administrator configure the VM instance-principal group, container resource-principal group and compartment-scoped permissions. Prepare VCN/subnets, routes, DNS and NSGs outside the application.
  3. Have the DBA prepare source and target schemas/accounts. The source needs replication/full-image settings and a stable table primary key. The target schema needs audit-table/state preparation rights.
  4. Create permitted Vault password secrets and identify an existing encryption key for a dedicated fingerprint secret. A database password and fingerprint key serve different purposes.
  5. Obtain the official MySQL 9.x Linux generic tarball URL for the VM architecture and its independently verified SHA256.
  6. Clone the repository on the VM and create private deployment JSON locally from examples/deployment.example.json. Fill real values on the VM; do not publish them or copy another installation's private identity.

Keep the private configuration directory mode 0700 and JSON mode 0600. The selected compartment_id and region must match the VM. Source endpoint login testing does not verify which OCI DB system owns an IP.

Preconditions that can block setup

A missing or invalid configuration, non-OL9 OS, wrong interpreter, invalid MySQL checksum, unsupported server major version or insufficient sudo/network access prevents completion. Resolve the cause before rerunning. Setup is rerunnable, but is not a MySQL major-version migration tool.

8. IAM and database access checklist

The VM uses its instance principal for OCI management. Container Instances use their own resource principals for private images, secrets and Streaming data access. The container does not inherit VM permissions. The application does not switch to user API keys when access is denied.

OCI administrator tasks

Use the full IAM policy guide, replacing placeholders with the actual identity-domain/group subjects and VM compartment. Grants depend on enabled features. Typical capabilities include container lifecycle, private repositories, permitted secret metadata/bundles and use of existing network attachments.

manage stream-family in the VM compartment covers OCI streams and stream pools. Native produce/consume permissions are needed for the relevant principal. Container principals need permitted produce/consume/read access and secret/repository access separately. A list success proves that read operation only.

App ownership tags guard app actions but are not an IAM isolation boundary. Review dynamic-group membership, especially rules that match every Container Instance in a compartment. The application cannot authorize changes outside its compartment merely because a broader IAM policy exists.

Setup and installation

9. First working flow: setup order

  1. Verify the OL9 application and embedded repository login. Run setup/access checks.
  2. Register source and target connections using Vault password references; test both.
  3. Review source ROW/FULL binlogging, GTIDs, retention, stable keys and grants.
  4. In OCI resources, select/create the active Streaming pool and data stream. Register the pool connection without a username or messaging token.
  5. Build/publish the native Debezium and writer images in the private registry. Select compatible digest-pinned releases and private workload networking.
  6. Register a mapping: one table, database.* or *.*; choose target grouping and End, Start or Specific GTID. End is the default and avoids a row-copy snapshot.
  7. Run source checks. Prepare/select the data stream; prepare the single-partition schema stream audit_<flow-id>. Deployment also prepares the schema stream automatically.
  8. Deploy. Confirm the source task and writer are running, then verify queue arrival and newest target events/checkpoints.
  9. Use approved isolated CREATE/UPDATE/DELETE operations to verify typed keys, full images, actual source table labels and replay behavior.

Keep a reviewed record of stream IDs, source lineage, offsets, JDBC history, fingerprint secret and delivery state. Container ACTIVE alone does not prove capture.

Configuration and capture design

16. Source scopes and target layouts

A mapping selects which source row changes belong to a flow and how the writer organizes their audit history. The target uses fixed audit-event JSON columns; it does not recreate each source table's columns.

Source selection

Source selection Captured scope
sales.orders One named base table
sales.* Eligible base tables in one database
*.* Eligible base tables across source databases

Use the database and table selectors in Register table. The wildcard is a whole-name choice; partial patterns such as sales.order* are not supported. Literal names are escaped when constructing Debezium's anchored regular-expression filters. Internal/system databases are excluded. Registered audit-target schemas on the same source server are excluded to prevent capture feedback.

Source checks inspect metadata and primary keys, not table contents. Current inventory is limited to 1,000 tables; a larger result is rejected rather than silently truncated. Every included table needs a complete stable primary key. A new table or database that matches the saved scope can be discovered while capture runs. A newly created keyless table is not silently ignored: unsupported row events stop the writer for review. Review filters and exclusions when adding new databases, audit destinations or broad source registrations.

Broad capture increases schema/change volume and may include sensitive application data. Choose the narrowest scope that meets the audit requirement. Source account permissions and metadata visibility must cover the intended databases; a wildcard does not grant MySQL privileges. Overlapping registrations on the same source and unsafe source-to-target feedback paths are rejected.

Target grouping

All three choices use the selected target connection and schema.

Grouping Physical audit destination
By flow One audit table for every source table in the flow
By source database One generated audit table per actual source database
By source table One generated audit table per actual source database/table pair

For example, sales.orders, sales.customers and billing.orders produce one, two or three physical audit tables respectively. By database does not create one target schema per source database. The registered target-table name acts as the root/prefix for generated destinations. Names include a deterministic hash of the complete source namespace and flow identity, remain within MySQL's name limit, and are recorded in durable route/ownership tables.

The writer creates a destination only after claiming ownership. It refuses an unowned existing physical table rather than treating it as an empty audit store. Interrupted creation can resume from its saved claim. The root table retains the flow's retention anchor even when generated destinations hold the row events.

Each event retains its actual source database and table. Row-key hashes include that namespace, so identical primary keys in different tables remain distinct. The flow has one writer lease, one source offset namespace, and its prepared data and schema streams. Grouping does not create a connector or stream per table. Writes to several physical destinations are recoverable commits, not one atomic cross-table/source transaction. Replay checks prevent supported duplicate events when a later grouped write or checkpoint fails.

Browsing and operating boundaries

Audit Center combines the flow's owned destinations for history and charts. Filter by source database/table; a primary-key lookup must identify one actual table (and a database for *.*). Audit partitions lets you choose a generated physical table. Large JSON pages sort event coordinates before loading selected payloads.

End and initial Specific GTID are supported for wildcard mappings without copying existing rows. Start requests an initial row snapshot across the included scope and can be expensive. Normal restarts and image replacements retain full offsets. Historical repositioning of an already deployed wildcard flow is disabled until complete schema-baseline coverage across all included tables can be proven. The single-table historical preview does not imply that capability for a wildcard.

Automatic retention cleanup for grouped targets is disabled. Use a separately reviewed, coordinated maintenance procedure that preserves the flow's payload, deduplication, delivery, schema, routing and fragment evidence together. A row count or an old root table alone is not sufficient cleanup evidence.

Once deployment history exists, source scope and target grouping are locked. Register a new flow for a changed data path; do not edit identifiers under saved checkpoints. See capture position, Streaming and size limits and coverage limitations.

Configuration and capture design

17. Streaming buffers, size limits and request control

The deployed path is source MySQL binlog → embedded Debezium Engine → native OCI Streaming → history writer → target audit store. The capture and writer use OCI SDKs over HTTPS with resource principals. No Object Storage overflow path is used. Ordinary events keep their original key and full Debezium envelope.

Why stage changes in a stream?

A durable stream lets capture publish while a writer is stopped, slow or being replaced. The writer later resumes from its target delivery checkpoint. Source capture and target apply can progress at different speeds, and short apply-side interruptions need not force an immediate source replay. Stream retention bounds this buffer: it is not an unlimited archive or a substitute for source binlogs.

There is a significant dependency in this implementation: the source offset and Debezium JDBC schema history are stored in the target database too. If the entire target database is unavailable, capture can also pause when it needs that state. Streaming decouples publishing from row apply, but does not make capture fully independent of the target database. Preserve enough source binlog retention for that outage and enough stream retention for the writer's recovery. An independent capture-state database would be an additional design change.

Debezium envelope overhead

The payload contains the operation, before/after values and source coordinates. The outer schema describes the serialized fields and their types. A two-column update can therefore carry far more metadata than changed business values. Source metadata describes the event's origin and replication position; database passwords and connection secrets are not part of the row message.

This release retains the complete schema and both images for supported updates. It does not silently remove fields or change typed fingerprint semantics. Debezium JSON serialization can omit repeated schema descriptions, but a compact mode needs an explicit schema recovery/versioning contract and compatibility validation. Such a mode is not implemented here. Removing unchanged columns or the BEFORE image would also change what audit history can establish. Fragmentation preserves information; it is not compression and adds some bytes and processing work. Debezium Engine serialization.

Snapshots read current source rows directly. End and Specific GTID establish schema and follow binlog events without a row-copy snapshot. A broad wildcard scope still increases metadata and change volume; skipping the snapshot does not remove the cost of reading and serializing large row changes. Debezium MySQL connector.

Fragment delivery and recovery

  1. The publisher measures the complete key/value. A normal event stays one message.
  2. An oversized event is packed with the original key and split. Each part includes its index/count, declared size, message identity and part/full SHA-256 checksums. A stable routing key keeps the parts of that event in one stream partition.
  3. The source checkpoint advances only after every required part was accepted. A partially accepted request cannot acknowledge an unpublished source event.
  4. The writer commits fragment custody before advancing the delivery checkpoint past an incomplete part. A restart can resume from those saved parts.
  5. Only complete, validated events enter the normal audit writer. The original before/after data, schema and key are reconstructed; partial events never become audit rows. Completed payload blobs are released after durable delivery state proves completion. Compact receipts remain for replay checks.

A source restart can regenerate processing timestamps in an envelope. That can produce a different fragment generation for the same underlying source event. An older incomplete generation is retained even when a later complete generation arrives. Source-coordinate deduplication protects supported row events, but does not automatically reconcile every abandoned fragment set. Review retained custody and source/delivery evidence before explicit cleanup. The pending limit stops further custody instead of silently discarding incomplete data.

Complete receipts, the event deduplication ledger and audit payloads have different lifetimes. This release does not automatically prune every receipt. Grouped target retention also requires coordinated maintenance. Neither source transactions nor writes across multiple target tables form one distributed atomic transaction.

Fewer requests before retries

Several small events share one PutMessages request while remaining separate OCI messages. A request is flushed when its byte budget, record count or destination requires it. Data and schema streams require separate requests. No custom aggregate wrapper is added around normal events.

A hot key can concentrate traffic in one partition, so increasing the rate or partition count does not guarantee higher usable throughput. Reading waits at least 250 ms between requests for the same partition and slows further for byte volume or idle queues. Backoff adds some latency when a quiet queue becomes active. Each source engine also has a bounded 64 MiB change queue.

Retries remain bounded fallback handling. HTTP success does not prove every PUT entry succeeded: the publisher checks individual results, including numeric 429, and retries only rejected entries. A failed batch retains the source checkpoint. GET retries retain the same cursor; target checkpoints move only after durable custody or audit commits. Partition throughput, API management quotas and workload lifecycle quotas are distinct constraints; identify the service and operation from the actual error rather than assuming PUT and GET share one global quota. Target size and browse limits

The target stores keys, images and schema as JSON in a fixed audit structure. It is not a column-for-column replica of the source's wide row. InnoDB page/row rules therefore differ from the total JSON payload size, and large values can use out-of-page storage. This does not make JSON or network packets unlimited. A JSON value is constrained by max_allowed_packet; client/server packet settings, writer memory, serialization expansion and batch size must also be adequate. MySQL JSON limits, packet limits, storage requirements.

Raising the application event limit cannot raise the database's limits. Test the largest full update, including both images and schema, under representative load. The writer bounds batch bytes; one assembled event can exceed that ordinary batch budget while remaining subject to the logical event ceiling. Audit Center pages sort lightweight event coordinates before retrieving selected JSON payloads, avoiding a large JSON sort. Selected payloads are still loaded for the page: many very large events can produce a heavy browser response.

Appendix I. DDL-driven row changes and audit coverage

This prototype cannot promise complete row history for DDL-driven data changes. MySQL logs DDL as statements even in ROW mode. FULL supplies columns in row events; it does not create individual row images for a partition swap or drop. Debezium and the writer cannot recover missing values from a DDL statement.

Operation What can happen Evidence limitation
EXCHANGE PARTITION ... WITH TABLE Swap a partition with an unpartitioned table No individual CREATE/DELETE for the exchange, even if both objects are registered
DROP PARTITION Usual INPLACE RANGE/LIST operation removes the partition and its data No per-row DELETE/BEFORE records
TRUNCATE PARTITION Empty chosen partitions without changing their definitions No per-row deleted images; structural delta can be empty
TRUNCATE TABLE / DROP TABLE Remove current table contents A table-level/schema event is not a list of deleted-row images
Column changes / defaults Alter existing logical values or discard a column No guaranteed UPDATE for every existing row

Exact effects depend on the supported MySQL version, engine and algorithm. DROP PARTITION with COPY can redistribute some rows rather than delete the entire old row set. REORGANIZE commonly preserves logical data while changing placement; physical movement is not automatically a logical UPDATE.

Schema history is not a partition-row snapshot

The separate public schema path can archive supported matching tableChanges, including available structure/DDL/source positions. It does not retain every partition row. The current writer has no raw-DDL catch-all; parser/version/filter behavior or no matching tableChanges can leave no schema record. Validate each exact statement on a test flow.

EXCHANGE can change millions of visible rows while retaining the same structure. An empty semantic_delta therefore does not prove unchanged contents. Client affected-row counts and before/after structure definitions are not row-set comparisons.

Effect on lookup, fingerprints and charts

A row removed through partition DDL can have an old CREATE/UPDATE and no later DELETE. A row brought in by exchange can have no CREATE. The most recent retained event is a last observation, not proof of current membership. Charts count captured events; a large DDL-driven change may not create a row-volume spike. HMAC fingerprints identify observed keys/values and do not prove capture completeness.

Restart, GTID repositioning, longer retention and ROW/FULL cannot synthesize absent events. A later snapshot is a new observation, not reconstruction of unavailable BEFORE values or intermediate changes. Do not label inferred differences as original Debezium DML.

Mitigation policy; not automated here

  1. Have the DBA review/limit data-impacting DDL on tables requiring complete row history. The prototype does not automatically block or flag every such operation.
  2. Where feasible and approved, use ordinary logged DML with capacity/locking/retention review for removals or imports requiring individual row evidence.
  3. For unavoidable DDL, preserve complete affected keys/rows and definitions before execution, including both sides of an exchange, at a coordinated source boundary.
  4. Preserve the statement/outcome/coordinates and a consistent after-state. Control concurrent writes with a DBA-approved procedure; counts/checksums alone do not recover row values.
  5. Retain separately derived reconciliation evidence and any coverage gap. Pre/post materialization, snapshot comparison and derived-event storage are not implemented features.

A separate audit log can identify a statement/actor/outcome but not every removed row. Preserved exchanged tables/backups may help recovery; a DDL-only log cannot restore values absent from all retained evidence.

Sources: MySQL binary-log formats, partition exchange, partition drop/algorithm semantics, TRUNCATE TABLE. See the full limitations guide for additional snapshot, retention, DCL, key and scaling boundaries.

Appendix J. HeatWave ETag issue and process errors

What failed and what changed

DB-system Start returned HTTP 412 NoEtagMatch even after fetching a fresh resource ETag. Some compressed GET responses used an ETag ending in --gzip. An uncompressed GET removed that representation suffix, but a subsequent resource-version mismatch still occurred. Compression was not the only observed cause; refreshing was not a sufficient remedy.

HeatWave OCI operations now omit ETag/If-Match. Oracle documents the lifecycle header as optional. The app keeps VM instance-principal authentication, exact compartment checks, required lifecycle state, request IDs and per-operation idempotency tokens. Deletion still requires app ownership and unused dependencies. It does not strip a suffix from an opaque ETag or change IAM to work around 412.

The read and action are not an atomic version lock. A concurrent operation can change state and OCI can still reject a request. A remaining 412 needs the requested action, resource name, last checked state, active work request and request ID for investigation. It is not automatically a password or IAM problem.

Why a writer can exit while its instance is ACTIVE

A stopped/unreachable target can cause MySQL 2003 during target connection or a lost-connection error during processing. OCI Container Instance lifecycle ACTIVE does not prove the application process is running. Debezium can independently retry a stopped source while its task still reports RUNNING.

Restore source/target DB availability, verify the configured connection and restart/resume the registered workload with existing checkpoints. Do not start every old INACTIVE instance; older stopped image versions can remain after replacements. Do not reset offsets, recreate streams or delete history to clear an attention badge.

What the latest-error display means

Each process block retains state/exit status and displays a compact latest safe logged error with time and relevant MySQL code. Clicking the process field opens its full diagnostic, including the failed step and next action. Examples include target connect, envelope decode, target/schema commit, checkpoint save and queue acknowledgement. Known codes are mapped to fixed guidance; raw exceptions, SQL, passwords and row values are not exposed.

Current images produce structured diagnostics. Older images may contain only an exception class, and unavailable log access is not proof that no error occurred. The display reports only evidence actually present and can show a historical error after a process recovers. Current health, queue arrival and target checkpoint progress remain separate checks.

Appendix K. Same-compartment resource limitation

HeatWave Audit Center is an independent prototype for evaluation and rehearsal, not an Oracle product. This installation supports one VM compartment and the VM region. OCI management calls use the VM instance principal. Private runtime configuration must match the compartment and region reported by the VM metadata service; selecting another compartment or switching credentials is not a bypass.

This is an application design restriction. It is not a statement that OCI services universally prohibit cross-compartment architectures. Shared resources in another compartment are outside this prototype's supported deployment model, even when an IAM policy could permit access.

The secret dropdown lists metadata and names, never plaintext secret values. Empty lists or denied metadata access do not authorize selecting from a different compartment. Restore the intended VM principal access or create the resource in the VM compartment. Check which principal needs access: the VM manages/tests resources, while containers independently resolve credentials and pull images using their resource principals.

Selecting a compartment-local secret is not a relocation of its existing Vault. When provisioning existing/shared resources manually, keep both the secret and its Vault/key in the selected boundary. New account/fingerprint setup explicitly checks the selected Vault/key attachments. The prototype does not implement a cross-compartment credential-sharing or secret-migration workflow.

Database addresses are a separate limitation

Connection registration accepts a database hostname/IP, port, database, username and selected Vault reference. It tests actual MySQL connectivity/login over TLS. It does not require a DB-system OCID or infer resource ownership from the address. A successful host-only connection test does not prove the database's OCI compartment. Operators must place the source/target DB systems in the intended compartment and verify their placement independently. The OCI HeatWave resource controls perform resource-ID compartment checks, but those checks do not turn an unassociated host-only registration into an attested DB-system identity.

Catalog and IAM distinctions

Shapes, service versions and Oracle-owned default configuration catalogs are service-supplied choices, not resources created by this app in another customer compartment. Selecting an Oracle default configuration omits a foreign custom configuration reference. Tenancy-level IAM groups, dynamic groups and policies must be prepared by an administrator; the application does not create or change them.

Troubleshooting and future scope

  1. Confirm the VM compartment/region and configured principal before investigating an empty resource dropdown or OCI 403/404.
  2. Confirm the resource is ACTIVE/available and located in that compartment. Credential lookup requires secret metadata and secret-bundle access; creation additionally needs permitted Vault/key operations.
  3. Check the VM and worker principal permissions separately. Do not broaden access or switch to API-key credentials to avoid the application boundary.
  4. Preserve fingerprints, offsets, checkpoints, identity tags and secret values during any planned migration. The app does not automatically move/adopt shared resources or rewrite existing audit history.

Supporting multiple resource compartments or regions would require an explicit scope model, separately approved IAM/network access, attachment validation, credential handling and migration/recovery tests. Editing an OCID in private JSON alone is not that implementation.
